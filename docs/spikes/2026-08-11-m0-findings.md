# M0 Risk Spike Findings

Three assumptions carry the fpd design. Each spike answers one, with throwaway code that
is deleted afterwards. Raw capture output is preserved alongside this document.

| Spike | Question | Result |
|---|---|---|
| S1 | Can a recording wrapper tee raw bytes under `tokio-rustls` and still complete a handshake, with extension **order** recoverable? | **PASS** |
| S2 | After manually consuming the h2 preface, can the connection still be served? | **PASS** |
| S3 | Can `boring` emit a ClientHello matching a captured Chrome? | **PASS** (go/no-go), extensions partial |

---

## S1 — Recording ClientHello under tokio-rustls · **PASS**

**Setup.** `spikes/s1-recording-stream`. A `Recording<S>` adapter implementing
`AsyncRead` tees every byte into an `Arc<Mutex<Vec<u8>>>`; `tokio-rustls` performs the
handshake on top of it; the buffered bytes are then walked independently to extract
cipher suites and extension IDs in wire order. Self-signed cert via `rcgen` 0.14 with
SANs `localhost` and `127.0.0.1`, ALPN `h2, http/1.1`.

**Drivers.** curl 8.x (HTTP/1.1 and HTTP/2) and Google Chrome on macOS, ~30 handshakes.
Raw output: `s1-capture-raw.txt`.

### Result

The handshake completes and extension order is fully recoverable. rustls' own
`ClientHello` accessor was never needed or used — confirming the design decision in spec
§6.2 to parse the buffered bytes independently.

```
curl    ciphers (49)  extensions (6)   [43, 51, 11, 10, 13, 16]   GREASE 0/0
Chrome  ciphers (16)  extensions (17)  order differs every connection   GREASE 1/2
```

### Findings that changed the design

**1. Capture survives handshake failure.** Chrome rejected the self-signed certificate
with `CertificateUnknown` on most connections, yet the ClientHello was still captured in
full — the tee happens before the alert. This is a robustness property worth keeping:
`serve` will fingerprint scanners and misconfigured clients that never complete a
handshake, which are exactly the connections an operator most wants to see.

**2. GREASE values rotate; only positions are stable.** Chrome's cipher[0] was observed
as 2570, 6682, 14906, 19018, 23130, 27242, 35466, 43690, 47802, 51914, 56026, 60138 and
64250 across successive handshakes. Profiles must therefore store GREASE as positions
plus a count, and comparison must normalise GREASE to a placeholder. Storing literal
values would have made every Chrome comparison fail.

**3. Extension 41 (`pre_shared_key`) does not permute.** RFC 8446 pins it last. Every
18-extension sample ended with 41 while the other 17 shuffled freely.

**4. Cipher order is fixed even for Chrome — only extensions permute.** The 15 non-GREASE
ciphers held identical order in every sample. The two axes are independent.

**5. Extension count varies by session.** The same browser produced both 17- and
18-extension handshakes, the difference being `pre_shared_key` on resumption. JA4's
extension-count digit is therefore not stable across a resuming browser.

**6. No SNI when connecting by IP.** Extension 0 was absent for both curl and Chrome,
since the target was `127.0.0.1`. This is precisely the distinction JA4 encodes as `d`
vs `i` in its first segment, observed rather than read.

Findings 2–5 are recorded in spec §6.9. Each would otherwise have produced a permanently
flaky equivalence comparison in M5.

### Illustrative permutation

Same browser, same target, three consecutive connections — identical sorted sets,
different wire order:

```
[64250, 10, 11,  5, 27, 65281, 23, 17613, 65037, 45, 13, 43, 18, 16, 51, 35,  2570]
[10794, 11, 23, 43, 17613, 51, 10,  5, 16, 65037, 13, 27, 65281, 18, 45, 35, 60138]
[19018,  5, 18, 51, 11, 35, 65281, 16, 13, 65037, 27, 17613, 43, 23, 45, 10, 56026]

sorted (all three): [5, 10, 11, 13, 16, 18, 23, 27, 35, 43, 45, 51, …GREASE…, 65037, 65281]
```

**No fallback needed.** The contingency in the plan — pre-reading the first TCP record
before handing the socket to rustls — is not required.

## S2 — Replaying a consumed h2 preamble into hyper · **PASS**

**Setup.** `spikes/s2-h2-replay`. TLS listener with ALPN restricted to `h2` so the client
is forced down the path under test. After the handshake the preface, SETTINGS,
WINDOW_UPDATE and HEADERS frames are read manually and appended to a buffer; the
connection is then wrapped in a `Replaying<S>` adapter that yields the buffered bytes
before falling through to the live socket, and handed to
`hyper::server::conn::http2::Builder::serve_connection`.

**Driver.** curl 8.7.1, HTTP/2. Raw output: `s2-capture-raw.txt`.

### Result

```
preface: OK
frame SETTINGS      len=18  flags=0x00 stream=0
frame WINDOW_UPDATE len=4   flags=0x00 stream=0
frame HEADERS       len=30  flags=0x05 stream=1
captured 103 bytes of preamble
>> SERVED OK after replay
```

curl received `HTTP/2 200` with the expected body. **`fpd serve` can capture the
fingerprint and still terminate the connection with hyper.** The frame-level proxy
contingency is not needed.

### Findings

**1. The Akamai-relevant fields are all available before the request is served.**
Measured for curl 8.7.1: `3:100;4:10485760;2:0 | 1048510465 | 0 | m,s,a,p`. Recorded in
spec §6.1, replacing previously unverified reference values.

**2. SETTINGS arrive out of ascending order — `3, 4, 2`.** Any implementation that sorts
or normalises settings destroys the fingerprint. This is the concrete justification for
modelling `settings` as an ordered `Vec<(u16, u32)>` rather than a map.

**3. `3:100` confirmed as the curl tell.** `SETTINGS_MAX_CONCURRENT_STREAMS = 100` is
present, as spec §6.1 predicted. No browser sends id 3 at all, so its presence alone
separates curl-family clients from browsers.

**4. WINDOW_UPDATE 1048510465 = 1048576000 − 65535** — curl raising the connection window
from the protocol default to 1000 MiB. A client configuration artefact, which is exactly
why it discriminates.

**5. Pseudo-header order `m,s,a,p` independently confirmed** from curl's own verbose
output (`:method, :scheme, :authority, :path`), matching the spec's curl row and
differing from Chrome's `m,a,s,p`.

**6. Frame-header parsing bug found and fixed — worth carrying into M3.** The stream
identifier occupies bytes **5..9** of the 9-byte frame header, not 4..8. Reading it one
byte early swallows the flags byte and produces values like `0x05000000` (83886080) for
what is really stream 1 with `END_STREAM|END_HEADERS`. The bug is silent: frame
boundaries stay correct, so everything else parses fine and only the stream ID is wrong.
M3's production reader must have a test asserting `stream_id == 1` for a first request.

### Not answered by this spike

HPACK decoding was skipped — the spike prints the SETTINGS and WINDOW_UPDATE portions of
the fingerprint but not the header list. M3 needs a real HPACK decoder to produce JA4H
and the pseudo-header order programmatically rather than reading it off curl's verbose
output.

## S3 — BoringSSL against a captured Chrome · **PASS on the go/no-go**

**Decision this spike existed to make: emulation (M5) stays in v1.**

**Setup.** `spikes/s3-boring-ja4`, self-contained: runs its own S1-style capture
listener, drives a Chrome-configured `boring` 4.22.0 client at it, and diffs in-process
against the Chrome baseline captured in S1. GREASE is normalised away before comparison,
per S1 finding 2. BoringSSL compiled from source in 50s on this machine.

**Baseline.** The Chrome capture from S1, GREASE removed.

### Result

```
=== boring output ===
  ciphers (16):    [GREASE, 4865, 4866, 4867, 49195, 49199, 49196, 49200,
                    52393, 52392, 49171, 49172, 156, 157, 47, 53]
  extensions (14): [GREASE, 0, 23, 65281, 10, 11, 35, 16, 13, 51, 45, 43, GREASE, 21]

=== vs captured chrome ===
  ✓ ciphers        15/15 exact order
  ✗ extensions     got 12 want 15
      missing: [5, 18, 27, 17613, 65037]
      extra:   [0, 21]
  ✓ GREASE         1 cipher, 2 extension
```

**Two of the three axes matched on the first attempt, with no tuning:** cipher order
exactly, and GREASE placement exactly (`set_grease_enabled(true)` puts GREASE where
Chrome puts it — cipher[0], extension[0], last non-PSK extension).

### The extension gap is enumerable and every item has an API

Each missing extension was checked against `boring` 4.22.0 rather than assumed:

| Ext | Name | How to add | Verified |
|---|---|---|---|
| 5 | `status_request` (OCSP) | `enable_ocsp_stapling()` | safe API present |
| 18 | `signed_certificate_timestamp` | `enable_signed_cert_timestamps()` | safe API present |
| 27 | `compress_certificate` | `add_certificate_compression_algorithm()` | safe API present |
| 65037 | `encrypted_client_hello` (GREASE) | `set_enable_ech_grease()` | safe API present |
| 17613 | `application_settings` (ALPS) | `boring_sys::SSL_add_application_settings` | **no safe wrapper**; FFI symbol confirmed present in the bindgen output at `target/…/boring-sys-*/out/bindings.rs` |

ALPS is the only item requiring unsafe FFI. BoringSSL itself supports it — the signature
is in the vendored `ssl.h` at line 3006 — but `boring` 4.22.0 ships no Rust wrapper. M5
either calls the FFI directly or contributes a wrapper upstream.

Also available and not yet exercised: `set_permute_extensions()`, which is how M5 will
reproduce S1 finding 1 (Chrome's per-connection extension shuffling).

### The two "extra" extensions are not real gaps

- **0 (`server_name`)** — a test artefact. The spike passed `"localhost"` as the SNI
  hostname while the Chrome baseline was captured over a connection to a bare IP, where
  Chrome correctly omits SNI. Same-input comparison will eliminate it.
- **21 (`padding`)** — BoringSSL pads the ClientHello to a size threshold; Chrome's was
  already past it. Since the five missing extensions add bytes, this difference is
  likely to disappear on its own once they are added, and should be re-measured rather
  than fixed directly.

### Consequence for the plan

M5 proceeds as specified. Its work queue is exactly the five rows above plus
`set_permute_extensions`, and the release-strategy hedge in spec §11 (shipping
inspection-only v1 and deferring emulation to v2) is no longer needed on technical
grounds — it remains available purely as a scheduling choice.
